## Engines and durability

On Apple platforms `fsync` returns once data reaches the drive's volatile cache; only `F_FULLFSYNC` survives power loss. Engines are compared within a class, and against the power-safe class. ## Method

- **Harness.** `tools/lilia-bench` builds one binary per engine group (no engine's native libraries are linked into another's measurements) and runs every workload group of every engine in its own process. Each write workload starts from an empty database directory.
- **Data.** 16-byte keys whose first 8 bytes are a hash (inserts land at random positions in every ordered index), 256 B values of mixed text, 1000000 records for reads and YCSB.
- **Durability.** Every engine runs in its most durable configuration; a write call returns after the engine's commit sync. The sync primitive is declared per engine and checked against the observed single-commit latency.
- **Time boxes.** Throughput workloads run for 5000 ms of wall-clock time each; throughput is operations completed divided by elapsed time. Point-read latency is sampled every 8th read so the clock does not dominate sub-microsecond reads.
- **Caches.** "Reopened" reads run right after closing and reopening the engine (cold engine caches); the OS page cache is not purged, which needs root.
- **Correctness.** Reads verify that every loaded key is found, scans verify the record count, JSON reads verify extracted values, analytics answers are compared with the value computed from the generator, and vector search reports recall@10 against an exact scan. A wrong answer fails the run instead of producing a number.
- **Resources.** Device bytes come from the process's own I/O counters (`proc_pid_rusage` on macOS, `/proc/self/io` on Linux) and include background threads; write amplification is device bytes written divided by payload bytes (keys + values). Disk size is measured with the engine closed.
- **YCSB.** Workloads A–F with a Zipfian (θ = 0.99) request distribution over the loaded records; every update or insert is its own commit.
