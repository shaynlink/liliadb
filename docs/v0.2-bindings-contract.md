# Contrat des bindings v0.2 (alpha.3c)

Ce document fixe ce que chaque binding expose après le basculement de SQLite vers `lilia-db`
(RFC §7, alpha.3c). Décision du 2026-11-21 : **basculer maintenant, retirer le reste**. Une
fonction dont `lilia-db` n'a pas l'équivalent disparaît des bindings jusqu'à son portage ; elle ne
reste ni en façade ni à moitié branchée (RFC §5.2).

Bindings concernés : `lilia-node-native` et `@liliadb/node`, `lilia-ffi` et les paquets Flutter,
React Native, Apple (SPM) et Android, `lilia-wasm` et `@liliadb/wasm`, `lilia-daemon` et
`lilia-protocol`, `lilia-cli`.

## 1. Couche commune

- **Ouverture** : `lilia_db::Database::open` (natif) ou `open_with` sur le `PoolVfs` d'un
  `OpfsPool` (navigateur, dans un worker dédié). Options exposées : durabilité, ledger,
  `history_retention`, `undo_depth`, profil matériel. Les options SQLite (`busy_timeout_ms`,
  `writer_queue_capacity`, `vfs`, tiers mémoire, codec de chiffrement) disparaissent.
- **Lots** : le format filaire reste `lilia_core::BatchOperation` (JSON et MessagePack). Une seule
  conversion `BatchOperation → lilia_db::Write`, dans `lilia-db` (module `wire`), sert tous les
  bindings ; une opération sans équivalent est refusée avec `UNSUPPORTED`, et le lot entier échoue.
- **Opérations** : `lilia-protocol` définit les opérations des bindings (`Operation`) et leurs
  résultats (`ResponseValue`) ; `lilia_protocol::execute` les exécute par la session système. Le
  daemon (IPC et passerelle HTTP) et Node passent tous par lui : une opération a le même sens
  partout. `lilia_protocol::open` et `close` ouvrent une base depuis les options ci-dessus (noms
  lus par `lilia_protocol::names`) et la ferment quand les appels en cours ont rendu la main.
- **Codecs du daemon** : une connexion s'ouvre par le préambule de son codec, `LRK1` (`rkyv`
  dans les deux sens, clients Rust) ou `LJS1` (clients JavaScript : requêtes en `MessagePack`,
  réponses en trames JS). Une trame JS est un texte JSON, écrit directement depuis les documents
  binaires et lu par le `JSON.parse` natif du client, suivi des octets bruts (clés, valeurs,
  vecteurs) qu'il désigne par numéro de segment. Le protocole passe en version majeure 2.
- **Erreurs** : `lilia_db::Error` → `LiliaError` (`From`, déjà dans `lilia-db`) ; les codes
  d'erreur des bindings ne changent pas. Les conflits restent `retryable`.
- **Sessions** : chaque appel passe par une `Session` ; un contexte de sécurité fourni à l'ouverture
  ou à l'appel garde la sémantique RLS et masquage de la v0.1.
- **Versions** : la version d'un enregistrement est la séquence moteur de son écriture, et non plus
  un compteur par enregistrement (1, 2, 3...). `if_version` garde sa sémantique (`0` : absent) ;
  les tests qui comparent une version à `1` changent.
- **Limites** : un `limit` absent ou nul lit tout ; il n'y a plus de plafond implicite à 1 000.

## 2. Ce qui reste

| Preuves ZK | CLI `zk setup`, `commit`, `prove`, `verify` | `lilia-zk` ; `commit` et `prove` lisent le document par `json_get` | la fonction SQL `zk_verify` est retirée |

## 3. Ce qui est retiré

| Fonctionnalité | Bindings touchés | Retour prévu |
|---|---|---|
| Blobs adressés par contenu (`blob_*`) | Node, CLI | journal de valeurs (RFC §5.3) |
| Partitionnement (`sharding_*`) | Node | aucun : la compaction et les politiques de rétention remplacent le découpage en fichiers ; l'archivage revient avec la sauvegarde |
| Requêtes vivantes, abonnements, CDC (`live_query`, `subscribe`) | Node, daemon | flux du journal (RFC §4.7) |
| Vues matérialisées (`*_materialized_view`) | Node, daemon | IVM sur le journal |
| Horloges hybrides et conflits (`hlc_*`, `json_*_hlc`, `*_conflict`) | Node, daemon | sync P2P |
| Synchronisation P2P | daemon | IBF sur le journal |
| Compression par dictionnaire (`json_train_dictionary`, `auto_train`) | Node, daemon | compression des blocs |
| Fonctions WASM (`*_wasm_udf`) | Node, FFI | retiré (RFC §5.3) |
| Embeddings automatiques (`vector_search_text`, `wait_for_embeddings`, `auto_embed`) | Node | `lilia-embed` reste une bibliothèque d'embeddings sans base |
| Chiffrement par codec | tous | chiffrement natif |
| Sauvegarde (`backup`), `vacuum`, taille de fichier, `prepare_for_background` | FFI, Node, CLI | point de contrôle du manifest |
| Lecteur SHM (`shm_reader_*`) | FFI, daemon | SHM 2, alpha.5 |
| Plugins (`lilia-plugin-api`, plugins `codec`, `sql`, `json`, `kv`, CLI `plugin`) | CLI | quand `lilia-db` aura un point d'extension réel (codec du chiffrement natif, fonctions DataFusion) |
| Fonction SQL `zk_verify` | SQL | fonction DataFusion, si un usage la demande |

Les tests qui couvrent une fonction retirée sont supprimés avec elle ; ceux du reste sont portés et
doivent passer.

## 4. Ordre de travail

1. `lilia-db` : module `wire` (`BatchOperation → Write`), statistiques, vérification d'intégrité,
   recherches composées (couche commune) ; tests.
2. Node : `lilia-node-native`, `@liliadb/node`, avec `lilia-daemon` et `lilia-protocol` dans le
   même commit que `lilia-graph` (premier état où l'espace de travail recompile). Le module
   natif n'expose plus que `open`, `close`, `execute` (pool libuv) et `executeSync` (dans un
   tampon réutilisé) : opérations en `MessagePack`, résultats en trames JS ; `@liliadb/node` a
   un seul client, sur le module natif ou sur le daemon, et
   chaque appel y est défini une fois pour l'API asynchrone et l'API `sync`.
3. FFI, puis Flutter, React Native, Apple, Android.
4. wasm et `@liliadb/wasm` (worker dédié, `OpfsPool`).
5. CLI.

Chaque étape compile, passe ses tests et est committée seule ; la suppression des crates SQLite
suit (étape 6 du plan alpha.3c).
